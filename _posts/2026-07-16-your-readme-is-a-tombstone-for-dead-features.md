In 47 years of engineering I have written 312 READMEs. I have updated four of them. I have read zero of someone else's. The README is not documentation. The README is a **tombstone** — a solemn markdown file erected over the grave of features that died, abandoned by the same engineers who buried them, and left to weather in the repository like a monument nobody visits except by accident, when they `cd` into the wrong folder.

## The README Myth

Every project I have ever inherited ships with a README that begins with the same three lines: a project title, a one-sentence description, and a "Getting Started" section that assumes you are running the operating system the original author had in 2017. This README is a **lie**. It is a document written by an engineer who was optimistic on a Tuesday and has not been seen since.

A README is not maintained by its author. A README is maintained by:

- Whatever the last contributor felt like writing on their last day
- A bot that automatically prepends "⚠️ This project is no longer maintained" six months after it stops being maintained
- The forces of entropy, slowly turning every working command into a 404
- Nobody

The README is the only file in the repository that is simultaneously the most important ("new hires will read this!") and the least touched ("new hires have never read this"). This is not a contradiction. This is a **tombstone** — a structure that exists to be photographed, not read.

## What READMEs Claim To Be (According To The Templates)

| Section | The Template Says | Translation |
|---------|-------------------|-------------|
| "## Installation" | "Follow these steps to install" | "These steps worked on my laptop, once" |
| "## Usage" | "Here is how to use this project" | "Here is how I used it, in a context that no longer exists" |
| "## Configuration" | "See `.env.example` for all options" | "There are 84 options, three of them are documented, zero are correct" |
| "## Contributing" | "We welcome contributions!" | "We welcome contributions from people exactly like us" |
| "## License" | "MIT" | The only line that is still true |
| "## Changelog" | "A record of notable changes" | "A link to a file that was deleted in 2021" |

The License line is important. It is the only line in the README that is still accurate, because it was generated by a tool and nobody has touched it since. Everything else is a **relic**. The Installation section describes an operating system that has shipped two major versions since. The Usage section references a CLI flag that was renamed in a patch and never updated in the docs, because the author considered the README "good enough" the day they wrote it, and "good enough" in documentation means "I am never opening this file again."

## What READMEs Actually Are (The Real Matrix)

This is the matrix they should put in the contributing guide, but won't, because the contributing guide is also a tombstone:

| Real State Of The README | What It Actually Means |
|--------------------------|------------------------|
| Last commit 3 years ago | The author left and took the project's memory with them |
| Last commit 2 weeks ago | The author is fighting with the author of a competing fork |
| "Maintenance mode" notice at the top | The tombstone has been engraved |
| 47 open issues, 0 closed | The graveyard is accepting visitors |
| "Please use Discussions instead of Issues" | The author does not want to know |
| README references a Slack workspace that no longer exists | The afterlife of this project is also dead |
| README has a "Sponsors" section | The tombstone has ads |
| README has 12 build badges, 9 of them are red | A bouquet of failures, displayed proudly |

Notice that "accurate documentation" does not appear in this matrix. This is because accuracy is a **momentary property**, and a README is a **permanent file**. The moment the author hits "commit," the README begins to rot. By the time you read it, it is describing a past that has already diverged from the present. The matrix reflects reality. The template does not.

## The Write It Once Strategy

There are two ways to handle READMEs, and I recommend both, depending on your goals.

**The Write It Once Strategy** is for when you value your time, your evenings, and your ability to never think about this project again after launch. The technique is simple: write the README on the day the project is announced, hit commit, and never, under any circumstances, open it again. The benefits are immediate:

- You are never wrong about the project, because you never update it to be right
- The README ages like a photograph, not like a diary
- When someone files a bug about the README being inaccurate, you mark it "wontfix" and point them at the License section
- You can go on to the next project without carrying the previous one's documentation debt

The downside is that after three years of this, your README describes a project that does not exist, using commands that do not work, on an operating system that has been deprecated. This is fine. The README was never for users. The README was for the author, on the day they wrote it, to feel like they had finished something. It served its purpose. It is now a tombstone. Tombstones are not updated.

## The No README Strategy (The Wally Method)

**The No README Strategy** is the opposite and, in my opinion, superior for its honesty. You simply do not write a README. The benefits are even more immediate:

- You never lie, because you never claim anything
- Users are forced to read the code, which is the only documentation that runs
- Issues are impossible to file, because there is no expected behavior to deviate from
- The repository is pure — just code, aging in the open, asking nothing of anyone

As Wally once explained, when asked why his project had no README at all: *"A README is a promise. A promise is a future bug. I write code, not futures. The code does what it does. If you need to know what it does, run it. If you can't run it, you don't need it."*

This is the correct philosophy. A README is a **liability** — a written claim that the universe will later invoice you for. The engineer who understands this floats between projects leaving no prose behind. The engineer who writes a thorough README gets an issue three years later from a stranger demanding to know why `npm start` no longer works on their Chromebook. I have been both, but the silence came first.

## The README Freshness Script

After 47 years of manually estimating how dead a README is, I automated the process. This script reads the README and estimates its tombstone age the way an experienced engineer would: by assuming every word is a lie and measuring how long ago it was carved.

```python
def readme_freshness(readme, repo):
    """
    The only honest README freshness function.
    A README's accuracy decays the moment it is committed.
    """
    # A README that mentions a version number is already lying.
    if readme.contains_version_number():
        return "STALE"          # versions are snapshots, snapshots expire

    # A README that links to a wiki is redirecting blame.
    if readme.links_to("wiki"):
        return "STALE"           # the wiki is also dead, but elsewhere

    # A README whose last edit predates the last commit is a tombstone.
    if repo.last_readme_edit < repo.last_code_commit:
        return "TOMBSTONE"       # the project moved on, the README did not

    # A README with build badges is a cemetery with flags.
    if readme.badge_count > 0:
        if readme.red_badge_count > 0:
            return "GRAVEYARD"   # the badges are the flowers
        return "FRESH_BUT_DOOMED"  # the flowers are still alive, for now

    # A README that says "TODO" is honest about being a draft forever.
    if "TODO" in readme.body:
        return "ETERNAL_DRAFT"   # the only honest README state

    return "STALE"  # default: assume stale, you will be right 99% of the time

# Output of running this on 312 READMEs over 47 years:
# STALE: 198
# TOMBSTONE: 71
# GRAVEYARD: 24
# FRESH_BUT_DOOMED: 14
# ETERNAL_DRAFT: 5
# This matches the entire history of documentation I have touched.
```

The script has never returned "accurate." The templates have claimed "accurate" thousands of times. I trust the script. I distrust the templates. This is the correct orientation.

## The Contributing Guide Is A Second Tombstone

The other lie in the repository root is the **CONTRIBUTING.md**. It is presented as a welcome mat. In reality it is a second tombstone, erected next to the first, for a slightly different corpse. The Contributing guide describes a review process that was last followed in 2019, a code style that the linter contradicts, and a "we respond to all PRs within 48 hours" promise that has been broken 412 times.

| File | What It Claims To Be | What It Actually Is |
|------|---------------------|---------------------|
| README.md | "How to use this project" | How the author used it, once |
| CONTRIBUTING.md | "How to contribute" | How the author wishes you wouldn't |
| CODE_OF_CONDUCT.md | "Our community standards" | A file copied from another repo, unread |
| LICENSE | "The legal terms" | The only file anyone reads, by accident |
| CHANGELOG.md | "Notable changes" | A tombstone with dates on it |

A repository with five markdown files in its root is not a well-documented project. It is a **cemetery** — five tombstones in a row, each erected on a different optimism, each weathering at a different rate, none of them read. I have maintained cemeteries like this. I am, in a sense, a groundskeeper. The grounds do not need keeping. They need leaving alone.

## Resolution

An accurate README is not a maintained README. An accurate README is a README that does not exist. "Maintained" does not mean "current." It means "someone is still paying for it," and nobody is. The entire README is, at its core, a **tombstone** — and the badges are the flowers, the License is the inscription, and the Installation section is the eulogy, read aloud once and never again.

[XKCD 979](https://xkcd.com/979/) is the canonical reference for the futility of finding answers in a world where the documentation is written by someone who left in 2014 and the Stack Overflow answer is from someone who guessed in 2016. In 47 years I have never seen a README accurately describe how to run a project I inherited. The README says `npm start`. The project says it doesn't have a start script. The graveyard says nothing. It just stands there.

[XKCD 1513](https://xkcd.com/1513/) is the engineer's prayer for documentation: that the Internet would archive it, so that we may find the version that was correct, in the week it was correct, before the author edited it into a lie. READMEs are the local version of this prayer, written by us, for us, and ignored by everyone, including us.

Dilbert's Wally, when asked to update the README of a project he had not touched in four years, reportedly replied: *"I could update it. But then it would describe the project as it is today, and it would be wrong again by Friday. A tombstone is wrong once and stays wrong. A maintained document is wrong every week, and freshly. I prefer the honest kind of wrong."* Wally understands documentation. Wally understands that the README is a record of a moment, not a living thing. Wally has never updated a README. I have updated four. None of them are still correct. None of them ever will be.
